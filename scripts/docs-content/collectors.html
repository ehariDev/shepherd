Connect a collector

Add a remotecfg block to the collector's config.alloy. Shepherd resolves the collector by its cluster and role attributes — role is one of metrics, logs, singleton, or receiver.

config.alloy
remotecfg {
  url = "http://shepherd:8080"
  basic_auth {
    username = "<token-uuid>"
    password = "<token-secret>"
  }
  attributes = {
    cluster = "<cluster-name>",
    role    = "metrics",
  }
  poll_frequency = "60s"
}

On first poll, an unclaimed cluster gets served an empty config so it keeps running whatever it already has locally — nothing is disrupted until an app admin claims the cluster for an organisation (Roles) and one of that organisation's admins enables pipelines that match it.

Over HTTPS

When Shepherd terminates TLS itself (Kubernetes or a bare-metal/VM install running as a systemd service), point remotecfg at the HTTPS URL and add a tls_config block if the certificate was issued by a private CA — the same thing your browser's trust store handles for you, spelled out for the collector instead:

config.alloy
remotecfg {
  url = "https://shepherd:8443"
  basic_auth {
    username = "<token-uuid>"
    password = "<token-secret>"
  }
  tls_config {
    ca_file = "/etc/pki/tls/certs/private-ca.pem"   // omit for a publicly-trusted certificate
  }
  attributes = {
    cluster = "<cluster-name>",
    role    = "metrics",
  }
  poll_frequency = "60s"
}

Shepherd cannot add this block for you. remotecfg is the collector's own bootstrap config — it is what the collector reads before it has ever talked to Shepherd, so nothing Shepherd serves can reach it. This is separate from the beacon's own tls_config (server.tls.collector_ca_file), which Shepherd does inject automatically into the served baseline pipeline that reports the collector's self-monitoring metrics back — see the changelog once that lands.
